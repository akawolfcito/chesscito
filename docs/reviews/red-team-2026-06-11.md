## Verified-real findings (actionable)

### P1 — Payment: `ledger_write_failed` (500) after on-chain transfer already landed
`apps/web/src/app/api/verify-payment/route.ts:285-286`. On a non-`23505` Supabase insert error (503, timeout, quota), the route returns 500 even though the stablecoin transfer is already finalized on-chain. The race re-fetch only runs on `23505`. User sees "payment failed" but they paid; a manual retry succeeds (idempotency pre-check catches it) and confusingly returns `duplicate:true`. **Fix:** on any insert error, re-check idempotency_key existence before returning 500; if the row exists, return success.

### P1 — Payment: orphaned payment, no auto-retry on verify failure
`apps/web/src/lib/payments/use-payment-rail.ts:192-193`. After tx confirms on-chain, a transient network error on the `verify-payment` POST leaves `phase:"error"` with no auto-retry/backoff. `verifyAgain()` exists but the user must trigger it manually, and `GetPeonesSheet` shows no "paid on-chain, retrying verification" affordance. **Fix:** auto-retry verify with backoff + a "confirmed on-chain, finalizing…" banner.

### P2 — Payment: PRO daily-quota race (concurrent spends bypass cap)
`apps/web/src/lib/peones/pro-bypass.ts:142-143` + `peones-spend-rpc.sql`. Quota is checked in app code before the RPC; the SQL `FOR UPDATE` lock guards balance but not the PRO-bypass quota. Two concurrent `/api/peones/spend` for the same wallet:target:day can both read `used=N`, both apply bypass. Impact bounded to one user/target/day. **Fix:** re-check quota inside the RPC after the lock, or serialize on wallet:target:day.

### P2 — Leaderboard: 429 mid-save has no backoff hint → retry loop
`apps/web/src/app/api/sign-score/route.ts:75-76` + `exercises-screen.tsx:1837,1897`. Sign rate limit (5/min IP, 3/min player) returns 429; the catch maps it to a generic "Try again" overlay with no `retryAfterMs`, so immediate retry re-hits 429. The off-chain `/api/scores/save` already returns `retryAfterMs` — sign-score should too. **Fix:** surface retry-after and disable the retry CTA until the window clears.

### P3 — Payment: multi-Transfer idempotency edge (`logIndex ?? 0`)
`verify-payment/route.ts:163`. The idempotency key uses `verdict.logIndex` (the matched Transfer), so a normal `ERC20.transfer` (single event) is **safe** — agent's HIGH rating was overblown. Only a custom batched tx with two treasury Transfers (one with undefined logIndex) could collapse to one credit. No current flow produces this. **Action:** note only; revisit if batched payments are ever added.

### P3 — Sign: signature deadline 10 min is generous
`apps/web/src/lib/server/demo-signing.ts:184-186`. ~120 Celo blocks of headroom; low risk. Consider 5 min for a tighter window.

## Steelman verdict — narrative & revenue

| Channel | Strength | Revenue credibility |
|---------|----------|--------------------|
| **MiniPay** | 7.5 / 10 | Medium-High (needs official listing) |
| **MetaMask / open web3** | 4.5 / 10 | Low (narrative is MiniPay-centric; no web3 positioning) |

**MiniPay case is strong and lived, not claimed:** 390px-first design, zero-click connect, direct stablecoin rail (no approve), monetization moments grounded in emotion (Coach at loss, Victory post-win, Shields at frustration). Free play is substantial and real.

**Where it breaks:**
1. **LTV is untested** — funnel map M1 is prescriptive, no cohort/conversion/renewal data. PRO at $24/yr is 2–4× below chess.com; depends on Coach paywall converting 5–10% and PRO retaining 40%+.
2. **Free→paid has no forcing function** — a player who only does exercises (never Arena, never loses) may never see a Coach paywall.
3. **Narrative fragments across surfaces** — landing ("casual learner") vs hub ("Welcome, friend", no promise) vs share cards ("can you beat this?" competition) vs shop ("buy stuff") tell four different stories.
4. **Peones language vs UI** — copy says "Peones" but HUD shows separate credits + shields counters.
5. **MetaMask** — 390px is a disadvantage on desktop; on-chain assets (Victory NFT/Badges) are framed as "proof" not "collectibles"; Coach (the revenue motor) is off-chain so web3 users may skip it → LTV collapse.

**3 highest-leverage fixes (from steelman, de-duped against current state):**
1. **Unify the narrative spine across surfaces** — one promise from landing → hub → share → shop. Highest leverage, lowest code cost.
2. **Add a forcing function into the Coach funnel** — nudge exercise-only players toward an Arena match / first Coach moment.
3. **If MetaMask revenue is a goal, author a web3-native narrative layer** — "own your victories on-chain," lead share cards with verifiable collectible framing. Otherwise, consciously treat MetaMask as fallback and don't invest.

> Note: the steelman's "decouple SaveScore" fix is **already largely done** — off-chain base save exists and on-chain SAVE was deliberately revived as the optional prestige layer (founder request, 2026-06-11). Its remaining gap is the 429-backoff UX (P2 above).
