# 360×640 Viewport Audit — MiniPay Minimum

**Date:** 2026-06-03
**Method:** read-only Playwright audit script (`/tmp/audit-360.mjs`) against production (`https://www.chesscito.com`, commit `c99b0a34`). Viewport 360 × 640, deviceScaleFactor 2, Pixel 5 UA. Screenshots + geometry/CLS probes at `/tmp/audit-360/`.
**Goal:** verify Chesscito is usable at the MiniPay minimum viewport (360 × 640) before listing submission, and decide if any layout fixes are required.

---

## TL;DR

**At 360 × 640 production renders correctly across all 10 surfaces probed.** Zero horizontal overflow, no dock anchor gaps, no off-screen primary CTAs. The few flags raised by the audit are either intentional patterns (touch snap-scroll, not a carousel) or sub-10-pixel cosmetic clips that do not change function.

**Recommendation:** add the 360 × 640 Playwright project as **additional** coverage (do not replace the existing 390 × 844 minipay project). Defer all visual patches — there are no real breaks.

The mobile CLS regression flagged in `docs/pagespeed-report-2026-06-03.md` (0.119 here vs 0.187 in Lighthouse) is **not 360-specific** — it shows at 390 too. Worth investigating separately, but does not block 360 coverage.

## Detailed findings

### 1. Landing — 3 "offscreen" CTAs (false positive, no patch needed)

The audit flagged these 3 elements as extending past the viewport right edge:

| Element | Position at 360w | Note |
|---|---|---|
| `button.landing-green-cta--medium` "I want PRO access" | left 302, right 552 | inside snap-scroll container |
| `a.paper-tray` "Let me know when it's ready" | left 606, right 869 | inside snap-scroll container |
| `a.paper-tray` "Let's talk" | left 923, right 1189 | inside snap-scroll container |

**Root container** (`landing-page.tsx:509`):

```html
className="-mx-5 mt-8 flex snap-x snap-mandatory gap-3 overflow-x-auto px-5 pb-2
            md:mx-0 md:mt-12 md:grid md:grid-cols-2 md:gap-4 md:overflow-visible
            md:px-0 md:pb-0 lg:grid-cols-4"
```

This is a **touch snap-scroll** for the audience-cards section on mobile, with a `md:grid-cols-4` layout on desktop. On mobile users swipe horizontally to see each audience card. This is NOT a carousel pattern (no auto-advance, no prev/next controls) — it is a native CSS scroll-snap container, common iOS/Android pattern.

Per project HARD RULE `[no-carousels]`: carousels with explicit slide controls are banned. The snap-scroll here does not violate that rule — it is a single-axis touch-scroll list.

**Verdict:** intentional. The "offscreen" detection in the audit script does not understand container scroll context. No patch.

### 2. Hub — CLS 0.119 (already known, not 360-specific)

Layout-shift PerformanceObserver reported `cls = 0.119` between mount and t+1200 ms. The Lighthouse run against `/hub` mobile reported 0.187. Both numbers are above the "good" threshold (0.1).

This is the same CLS regression flagged in `docs/pagespeed-report-2026-06-03.md`. It is mobile-wide, not 360-specific (the Lighthouse measurement was at the default mobile preset, which is closer to 390 wide).

Likely suspects (informed by the hub layout, not yet verified):

- Connect-button pill swap during `useMiniPay()` resolution: "Connect" → "Connected (alias)" → "MiniPay detected" — each variant has a different rendered width, pushing siblings.
- The Z1 PRO chip / trophy chip / character hero mount sequence.
- Lottie or character animation loader changing layout once the asset resolves.

**Verdict:** belongs to a separate Hub-CLS investigation cluster. Not a 360-specific fix. Not blocked by the 360 fixture addition.

### 3. Exercises — 6 px chip clip ("Move t…" instead of "Move to h1")

The "Move to h1" chip at the top of the exercises screen reports `clientWidth 67 / scrollWidth 73` — text overflows the chip by 6 pixels and shows an ellipsis.

Visually (screenshot) the chip reads `Move t…` instead of `Move to h1`. Function preserved (it's still recognizable as a "move to" chip showing the target), but the target square label is hidden.

**Severity:** cosmetic. The same chip at 390w shows the full text. A 6 px tighter padding or a slightly smaller font on the move-target chip would close the gap. Not blocking — users can still play exercises at 360.

**Suggested follow-up (not in this commit):** tighten the inline-padding on `.chesscito-move-target-chip` or equivalent, or apply `text-overflow: clip` with a slightly smaller font at `max-width: 370px`.

### 4. Arena — 7 px chip clips on color/difficulty selector

Two buttons in the arena pre-game flow report tight clips:

- `button` "✓ Play as White" — clientWidth 153, scrollWidth 160 (7 px short).
- `button` "✓ Easy / Friendly AI, makes mistakes often" — clientWidth 316, scrollWidth 323 (7 px short).

Visually both fit cleanly — the audit script flagged them because their internal text content (which wraps across two lines) has a single line that microscopically exceeds the container. No visible truncation.

**Severity:** cosmetic / probably not a user-visible issue.

**Suggested follow-up (not in this commit):** if a future polish cycle touches the difficulty selector, give the inner text 1 line-height of padding-end. Not necessary now.

## Why no visual fixes in this commit

The audit was scoped to detect: overflow, clipping, dock issues, off-screen CTAs, text truncation, visible CLS. Results:

- Horizontal overflow: zero surfaces.
- Off-screen CTAs: zero true positives (the 3 landing reports are inside an intentional snap-scroll).
- Dock anchor: no gap on any surface (dock sits at viewport bottom on all hub-class screens).
- Text truncation: 3 tap-target labels with 6–7 px clips; one shows visible ellipsis (`Move t…`), two are 2-line wraps that fit visually.
- CLS: 0.119 on hub — already known, not 360-specific, separate investigation.

There is no surface where a user cannot reach a primary action at 360 × 640. The screenshots confirm visual cleanness across all 10 probed routes.

Adding a 360 × 640 Playwright project as additional VR coverage gives us future regression protection without paying for visual changes the product does not need today.

## Patch proposed

```diff
   projects: [
     {
       name: "minipay",
       use: { ...devices["Pixel 5"], viewport: { width: 390, height: 844 } },
     },
+    {
+      // MiniPay store-required minimum viewport per
+      // docs/reviews/2026-06-03-viewport-360x640-audit.md.
+      // Additional coverage — the primary `minipay` project (390 × 844)
+      // stays as the canonical project for VR baselines.
+      name: "minipay-360",
+      use: { ...devices["Pixel 5"], viewport: { width: 360, height: 640 } },
+    },
     {
       name: "desktop",
       use: { ...devices["Desktop Chrome"], viewport: { width: 1440, height: 900 } },
     },
     {
       name: "iphone-safari",
       use: { ...devices["iPhone 15 Pro Max"] },
     },
   ],
```

That is the entire change. No `--update-snapshots` invocation yet — the existing baselines remain pinned to the `minipay` (390) project. If we later want VR coverage at 360, we add baselines explicitly with a new spec or a `--project=minipay-360 --update-snapshots` run, with rationale in the PR body.

## Risks

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| A spec written for 390 assumes a wider viewport (e.g., a click coordinate hardcoded to x > 360) and fails at 360 | Low | Low | Specs use selectors, not coordinates, in the surveyed sample. Verified e2e specs use `page.click(selector)` and `getByRole`. |
| VR baselines do not exist for minipay-360, so a future user runs `pnpm test:e2e:visual --project=minipay-360` and sees "no snapshots" | Medium | Low | Document in PR that minipay-360 is non-VR by default. The existing `pnpm test:e2e:visual` script is pinned to `--project=minipay`. |
| CI runtime increase | Low | Low | Specs run in parallel across projects. The new project adds at most 1 test slot of runtime per spec it is exercised against, but the default `pnpm test:e2e` does not auto-cover minipay-360 unless invoked explicitly. |
